# Test dependencies for the HA-harness (T2) test tier of the rgbcct_wled integration.
#
# !! DO NOT PIP-INSTALL THIS ON WINDOWS !!
# Home Assistant cannot be imported on Windows at all: homeassistant/runner.py has
# a bare, unguarded `import fcntl`, and fcntl is POSIX-only. Worse, the harness
# registers a pytest11 entry point that imports HA at pytest STARTUP, so installing
# this file on Windows breaks even the HA-free tests. Full detail in Dockerfile.test.
#
# This file is consumed by **Dockerfile.test** (Linux container). You should not
# need to install it by hand:
#     npm run test:python:ha     full suite in Docker  -> 850 passed, 153 skipped
#     npm run test:python        HA-free tier, native  -> 847 passed, 154 skipped
#
# The pure-logic tests (tests/test_color.py, test_models.py, test_payload.py) import
# nothing from Home Assistant and run on a bare `pytest` without this file at all —
# that is the point of `npm run test:python`, and the only place that HA-free
# property is actually verified (the container has HA installed, so it cannot).
#
# !! PYTHON VERSION MATTERS -- BUT DO NOT COPY THE NUMBER AROUND !!
# Home Assistant raises its minimum Python over time, and the harness below installs
# HA *as a library*, so the interpreter caps which HA you can simulate. The pin on
# the last line is the single source of that constraint: the chosen PHACC release
# declares its own `requires_python`, and pip enforces it. Dockerfile.test picks a
# base image to satisfy it and fails the build if it does not.
#
# Nothing outside the container needs this floor. `npm run test:python` runs the
# HA-free tests, whose only requirement comes from this repo's own code -- see
# MINIMUM_PYTHON_VERSION in scripts/python-env.mjs.
#
# To look the floor up rather than trust a comment:
#     pip download --no-deps pytest-homeassistant-custom-component==<version>
#     # or read requires_python at
#     # https://pypi.org/pypi/pytest-homeassistant-custom-component/<version>/json
#
# !! WHY THE HARNESS IS PINNED TO AN EXACT VERSION !!
# pytest-homeassistant-custom-component (PHACC) pins one *exact* homeassistant
# release per PHACC version, and declares a `requires_python` floor to match.
# pip treats an unsatisfiable `requires_python` as "this release does not exist"
# and keeps walking backwards until something installs -- so an UNPINNED install
# on too old an interpreter does not fail, it silently succeeds against an
# ancient HA. Measured: on Python 3.12, pip reports the newest available PHACC as
# 0.13.205, which pins homeassistant==2025.1.4 -- roughly 19 months stale at the
# time of writing. A mismatched simulator is worse than none, because it
# green-lights APIs the Home Assistant you actually run may not have.
#
# Verified from PyPI metadata (2026-08-08) -- PHACC version -> HA pinned:
#     0.13.205  homeassistant==2025.1.4   python>=3.12   <- the silent-downgrade trap
#     0.13.316  homeassistant==2026.2.3   python>=3.13
#     0.13.317  homeassistant==2026.3.1   python>=3.14   <- floor jumps to 3.14 here
#     0.13.339  homeassistant==2026.6.3   python>=3.14   <- pinned below
#     0.13.355  homeassistant==2026.8.1   python>=3.14
#
# TO TARGET A DIFFERENT HOME ASSISTANT RELEASE, re-pin to the PHACC version whose
# homeassistant== pin matches it, and check the python floor did not move with it.
# Pin to the release you actually run, not simply the newest.
#
# PHACC pulls in Home Assistant itself plus the test harness (the `hass`,
# `aioclient_mock`, `enable_custom_integrations` fixtures, pytest-asyncio,
# pytest-socket, etc.) and pins its own exact `pytest`, so do NOT pin pytest
# separately here -- the two constraints would conflict.
pytest-homeassistant-custom-component==0.13.339
